\chapter{Design \& Methodology} \section{Introduction} This chapter sets out the methodology I used to design, build, and experimentally validate the \textbf{Hybrid Rule-Based and AI-Assisted Penetration Testing Orchestration Framework}. The project follows a developmental and experimental methodology: I built a hybrid rule-based and AI-assisted orchestration framework that coordinates reconnaissance, scanning, web-security analysis, vulnerability mapping, threat-intelligence enrichment, risk prioritization, exploitation, post-exploitation analysis, MITRE ATT\&CK mapping, AI-assisted interpretation, attack-graph analysis, social-engineering simulation, and reporting, and I then evaluated that framework in a controlled laboratory environment using intentionally vulnerable systems and repeatable execution conditions. I deliberately designed the system to keep deterministic security decisions separate from probabilistic and generative components. Vulnerability severity, threat-intelligence enrichment, exploit-selection scores, risk scores, and the primary MITRE ATT\&CK mappings are all produced by deterministic or explicitly bounded analytical modules. Where machine learning could add extra ranking or classification evidence, I incorporated it as a supporting signal rather than letting it replace the rule-based controls. The local large language model sits downstream of the analytical pipeline and is restricted to generating report narratives and explanations. I introduced this separation to keep the data reproducible and to stop the generative model from touching technical facts that the framework had already calculated. The methodology breaks down into four main design principles. First, the penetration-testing lifecycle is represented as a twelve-stage pipeline coordinated by a central orchestrator. Second, classification and prioritization rely on a hybrid approach that combines deterministic rules, structured threat intelligence, semantic matching, and machine learning. Third, the framework records its findings as structured session data and exposes the same execution flow through both a command-line interface and a REST API. Finally, assessment results are turned into analyst-oriented outputs: JSON and PDF reports, MITRE ATT\&CK Navigator layers, attack-chain representations, Sigma-based detection mappings, and natural-language summaries generated by a local Qwen2.5 model through Ollama. The rest of this chapter is organized into four sections. Section~\ref{sec:overall-methodology} lays out the overall methodology and the reasoning behind the key technical choices. Section~\ref{sec:project-design} then applies these choices to the actual project design, covering configuration, algorithms, software components, the storage model, the API architecture, the deployment model, and the execution workflow. The performance measures defined in Section~\ref{sec:metrics} are the ones evaluated in Chapter~4. The chapter closes with Section~\ref{sec:summary}. \section{Overall Methodology} \label{sec:overall-methodology} This research follows a combined development and experimental approach, which fits applied cybersecurity work well: the contribution here is not just an algorithm description, it is an operational security framework whose behavior I could then observe under controlled conditions. I divided the development process into six broad activities. I first determined the functional and non-functional requirements using penetration-testing practice, the MITRE ATT\&CK Enterprise framework, OWASP guidelines, threat intelligence, and the project goals set out in Chapter~1. I translated these requirements into a set of discrete system modules with structured interfaces, then implemented the Python modules and the centralized orchestration logic that ties them together. AI-assisted integration added bounded machine-learning and language-generation capabilities on top of that base. I validated the framework experimentally against intentionally vulnerable systems in an isolated laboratory network, and finally carried out a performance evaluation against the quantitative and qualitative criteria defined in Section~\ref{sec:metrics}. Four complementary methodological families address the main research goals. The modular twelve-stage pipeline handles lifecycle automation. The hybrid MITRE ATT\&CK engine addresses adaptive attack classification. The multi-factor risk engine and exploit-prioritization model support risk-aware decision making. Explainability and analyst support are handled through the AI-assisted enrichment layer, the ATT\&CK visual outputs, the Sigma mappings, and the LLM report writer. \subsection{Overall Workflow and Lifecycle Automation} The framework is built around a series of twelve stages that represent a penetration-testing engagement. Each stage executes one security task and produces structured data that later stages consume. I chose this approach specifically to reduce the manual coordination that would otherwise be needed between separate tools. % ============================================================ % FIGURE 1 — Overall twelve-stage pipeline of the proposed framework % ============================================================ \begin{figure}[H] \centering \begin{tikzpicture}[node distance=8mm and 8mm] % Row 1: Phases 1-4 \node[stage] (p1) {Phase 1\\Reconnaissance}; \node[stage, right=of p1] (p2) {Phase 2\\Scanning \&\\OWASP Web Assessment}; \node[stage, right=of p2] (p3) {Phase 3\\Vulnerability\\Mapping}; \node[stage, right=of p3] (p4) {Phase 4\\Threat Intelligence\\Enrichment}; % Row 2: Phases 5-8 (below, right to left for snake layout) \node[stage, below=14mm of p4] (p5) {Phase 5\\Risk Engine\\(Filtering)}; \node[stage, left=of p5] (p6) {Phase 6\\Exploitation}; \node[stage, left=of p6] (p7) {Phase 7\\Post-Exploitation}; \node[stage, left=of p7] (p8) {Phase 8\\MITRE ATT\&CK\\Classification}; % Row 3: Phases 9-12 \node[stage, below=14mm of p8] (p9) {Phase 9\\AI-Assisted\\Enrichment}; \node[stage, right=of p9] (p10) {Phase 10\\Attack Graph\\Construction}; \node[stage, right=of p10] (p11) {Phase 11\\Social-Engineering\\Simulation}; \node[stage, right=of p11] (p12) {Phase 12\\Reporting}; % Main sequential arrows \draw[arr] (p1) -- (p2); \draw[arr] (p2) -- (p3); \draw[arr] (p3) -- (p4); \draw[arr] (p4.south) .. controls +(0,-8mm) and +(0,8mm) .. Exploitation, for example, is only attempted once discovered services have been linked to candidate vulnerabilities, enriched with current threat intelligence, assigned risk values, and ranked. The same logic applies to ATT\&CK mapping, which runs after exploitation evidence has been collected so that the mapping reflects the actual exploitation path, service, CVE, result status, and post-exploitation commands rather than a guess made too early. The pipeline also has explicit halt conditions built in. If reconnaissance finds no live host, the process stops there. Later stages are skipped when network scanning and web assessment return nothing usable, and the same principle applies after vulnerability mapping and risk filtering. This keeps unnecessary execution to a minimum and means every assessment follows a limited, predictable path. The automation I describe here refers specifically to end-to-end pipeline orchestration once an assessment run has already been started. The central controller automatically passes structured evidence between the twelve stages and applies the implemented transition, filtering, and halt conditions without requiring the analyst to shuttle outputs between separate tools by hand. This is a different claim from infrastructure preparation: external dependencies that particular components need, such as the Metasploit RPC service for Metasploit-based exploitation, still have to be available when those capabilities are called for. I treat their availability as an execution prerequisite rather than as a pipeline stage in its own right. When an optional or external dependency is missing, the corresponding capability may be reduced, or an implemented fallback may kick in where one exists; this does not license reading pipeline completion as a universal measure of automation. \subsection{Web Security Assessment Method} The second stage extends the network scan with a dedicated OWASP-oriented web-security engine. This web component is made up of seven specialized checkers: Injection, Broken Access Control, Authentication Failures, Security Misconfiguration, Vulnerable and Outdated Components, Cryptographic Failures, and Server-Side Request Forgery (SSRF). They are registered inside \texttt{OWASPEngine} and run in parallel through a bounded \texttt{ThreadPoolExecutor}. I did not intend this component to replace a full external web scanner; its job is to make sure web-application evidence is considered in the same context as network-service evidence. Different checkers gather evidence differently. The injection checker, for instance, performs a lightweight, error-based SQL-injection probe: it collects URLs that contain parameters, records a baseline response, modifies one parameter at a time using a single-quote probe, and only reports a finding if a SQL-error signature shows up in the probed response but not in the baseline. Other checkers rely on more specific, predefined assessment logic. For that reason I treat the web engine as a collection of specialized checks rather than as seven identical active-exploitation tests. Because the individual web-security checkers validate evidence in different ways, I do not assume their outputs carry the same evidential weight. Results backed by direct request/response evidence are treated as confirmed findings, while outputs based mainly on predefined or heuristic conditions are kept as candidate findings and read together with their recorded confidence and evidence fields. A typical web finding stores the OWASP identifier, CWE identifier, related MITRE ATT\&CK technique, CVSS base value, confidence, evidence, affected parameters, remediation guidance, host, port, and service. Together these fields create a direct evidence chain, shown in Figure~\ref{fig:web-finding-chain}. % ============================================================ % FIGURE 2 — Web finding evidence chain % ============================================================ \begin{figure}[htbp] \centering \begin{tikzpicture}[node distance=10mm] \node[proc] (wf) {Web Finding}; \node[proc, right=of wf] (owasp) {OWASP\\Category}; \node[proc, right=of owasp] (cwe) {CWE\\Identifier}; \node[proc, right=of cwe] (mitre) {MITRE ATT\&CK\\Technique}; \draw[arr] (wf) -- (owasp); \draw[arr] (owasp) -- (cwe); \draw[arr] (cwe) -- (mitre); \end{tikzpicture} \caption{Direct evidence link from a web finding to a MITRE ATT\&CK technique.} \label{fig:web-finding-chain} \end{figure} This chain can also be enriched through the NVD API. The \texttt{fetch\_nvd\_cves()} function queries NVD by CWE identifier and keeps the response in memory. If the network or the NVD service is unavailable, the finding stays valid on its local metadata alone, and the enrichment step returns an empty list instead of failing the scan. A \texttt{TechnologyDetector} complements the checkers by examining service product names, version strings, HTTP banners, selected headers, and Nmap HTTP script output. Recognized technologies get translated into likely attack-surface hints, and selected end-of-life version patterns can also be detected and optionally enriched with NVD data. Since the project needed a consistent result schema and a single unified pipeline, I chose to build this integrated design rather than lean entirely on an external web scanner. Tools such as ZAP, Nuclei, and Nikto can still be connected as extension points, while the core framework runs fine without any of the three. \subsection{Threat-Intelligence and Multi-Factor Risk Method} One of my goals for this project was to go beyond the theoretical severity of a finding and also weigh its practical security significance. The framework pulls together multiple sources of evidence before exploitation is even considered. \paragraph{CVSS Version Handling} The framework retrieves CVSS information primarily from NVD and, in the dedicated CVSS enrichment component, can also use CVEProject records. Because not every vulnerability record exposes the same CVSS generation, I did not assume a single CVSS version would be available for every CVE. The current implementation prefers CVSS v4.0 whenever it is present in the retrieved vulnerability record. If v4.0 is not available, the framework falls back to CVSS v3.1, then v3.0, then v2.0. Whichever version is selected is recorded together with the score and source wherever the enrichment path supports that metadata. So CVSS v4.0 is the preferred scoring standard in the framework, while older versions are kept for compatibility with historical vulnerability records. The threat-intelligence stage enriches findings with CVSS severity, the EPSS exploitation-probability score, CISA Known Exploited Vulnerabilities status, and other threat-score information. The Risk Engine then applies a bounded additive score: \begin{equation} R(v) = \min\Big(100,\ 4\cdot\text{CVSS} + \text{Type}_{\text{bonus}} + \text{Port}_{\text{bonus}} + 15\cdot\text{EPSS} + \text{KEV}_{\text{bonus}} + 0.10\cdot\text{TI}_{\text{score}} + \text{Service}_{\text{bonus}}\Big) \label{eq:risk-score} \end{equation} The score is capped at 100. Findings are then ranked by this risk score and by raw CVSS, and only those that clear the configured threshold proceed to exploitation, as Figure~\ref{fig:risk-scoring-workflow} shows. % ============================================================ % FIGURE 3 — Multi-factor risk-scoring workflow % ============================================================ \begin{figure}[htbp] \centering \begin{tikzpicture}[node distance=6mm and 10mm] \node[input] (cvss) {CVSS}; \node[input, below=of cvss] (type) {Exploitation-\\channel bonus}; \node[input, below=of type] (port) {Exposed-port\\bonus}; \node[input, below=of port] (epss) {EPSS}; \node[input, below=of epss] (kev) {KEV bonus}; \node[input, below=of kev] (ti) {External\\threat score}; \node[input, below=of ti] (svc) {Service bonus}; \node[proc, right=28mm of port, yshift=0mm] (risk) {Risk Engine\\$R(v)=\min(100,\ \ldots)$}; \node[decision, right=16mm of risk] (thr) {$R(v) \ge \theta$?\\($\theta=30$)}; \node[proc, above right=6mm and 12mm of thr] (yes) {Forwarded to\\Exploitation (Phase 6)}; \node[proc, below right=6mm and 12mm of thr] (no) {Excluded from\\Exploitation}; \foreach \n in {cvss, type, port, epss, kev, ti, svc} \draw[arr] (\n) -- (risk); \draw[arr] (risk) -- (thr); \draw[arr] (thr) -- node[above,sloped,font=\scriptsize]{Yes} (yes); \draw[arr] (thr) -- node[below,sloped,font=\scriptsize]{No} (no); \end{tikzpicture} \caption{Multi-factor risk-scoring workflow implemented by the Risk Engine.} \label{fig:risk-scoring-workflow} \end{figure} \subsubsection{Rationale for Risk-Scoring Weights} I built the Risk Engine as a heuristic risk-prioritization model rather than a statistically optimized one. I chose the coefficients and bonuses in Equation~\ref{eq:risk-score} to keep a transparent ordering between different sources of security evidence while holding the final score to a bounded 0--100 scale. CVSS gets the largest continuous contribution through the $4\times\text{CVSS}$ term, letting technical severity add up to 40 points without letting it decide the whole risk score on its own. EPSS contributes up to 15 points because it reflects predicted exploitation likelihood and is meant to add context rather than replace technical severity. KEV status gets a fixed bonus because it is direct evidence that a vulnerability has already been seen under exploitation, while the exploitation-channel and exposed-port bonuses capture whether a finding has a technically applicable attack path and whether the affected service is actually reachable. I multiplied the external threat-intelligence score by 0.10 so it could refine the prioritization without overpowering the assessment evidence gathered locally. The service bonus adds further context for services the framework treats as more security-sensitive. I set the exploitation threshold at 30 as an operational filter rather than an empirically optimized cutoff. Its job is to stop low-scoring findings from automatically moving into active exploitation while still letting through findings with enough combined evidence to be worth pursuing further. So neither the individual weights nor the threshold are claimed to be optimal — their role is to give the controlled laboratory experiments an explicit, reproducible, auditable prioritization policy. Empirically calibrating and running a sensitivity analysis on these parameters is left as future work. I rejected a simple likelihood-impact matrix as a modelling approach because the framework works on machine-readable numerical evidence. A conventional matrix is useful for manual risk workshops, but it loses information by squeezing evidence into a handful of discrete cells. The additive model keeps the contributions of CVSS, EPSS, KEV, service exposure, and exploitation context intact while staying simple enough to audit directly from the code. \subsection{Exploit Prioritization Method} Risk filtering decides which findings are significant enough to move forward to exploitation. A second, separate mechanism, implemented by \texttt{ExploitRanker}, then decides the order in which the technically feasible candidates should actually be attempted: \begin{equation} S_{\text{exploit}} = 0.25\,C_{\text{CVE}} + 0.20\,E_{\text{PSS}} + 0.15\,C_{\text{VSS}} + 0.10\,R_{\text{exploit}} + 0.10\,K_{\text{EV}} + 0.20\,P_{\text{ML}} \label{eq:exploit-score} \end{equation} where $C_{\text{CVE}}$ is CVE match confidence, $E_{\text{PSS}}$ is the EPSS value, $C_{\text{VSS}}$ is CVSS normalized to $[0,1]$, $R_{\text{exploit}}$ is the reliability assigned to the exploitation channel, $K_{\text{EV}}$ is one if the finding appears in KEV and zero otherwise, and $P_{\text{ML}}$ is the probability the trained prioritization model assigns to the high-priority class. I assigned the individual weights in Equation~\eqref{eq:exploit-score} heuristically, in decreasing order of how reliable I judged each evidence source to be — an exact CVE match, for instance, is treated as more trustworthy than a probabilistic score — rather than deriving them from a formal sensitivity analysis or an ablation study. I deliberately capped the weight on $P_{\text{ML}}$ at 20\% specifically so the machine-learning term could never dominate the deterministic evidence. Calibrating these weights empirically against labelled outcome data is noted in Chapter~5 as an item for future work. The resulting score sits in $[0,1]$. For every finding, a human-readable \texttt{selection\_reason} is also generated, documenting the main score inputs so the ranking can be explained during analysis. The machine-learning term does not replace the deterministic risk model — it only contributes 20\% of the exploit-selection score. When the trained model cannot be loaded, the framework falls back to a neutral probability of 0.50, which I chose so the exploitation stage keeps working even if the model file is missing. At execution time, fallback handling also applies at the level of the exploitation method itself. If a selected method fails or its dependency is unavailable, an alternative method is only attempted when it actually applies to the identified service and finding type — an unavailable Metasploit RPC path, for example, might be followed by credential testing through Hydra for supported services. Otherwise, the unsuccessful outcome is recorded as such rather than quietly turned into a successful result. The final exploit-prioritization model evaluated in this study was trained on \texttt{data/training\_data\_v2.csv}. This dataset is specific to exploit prioritization; the ATT\&CK classifier and the experimental post-exploitation classifier each use their own task-specific training data. The training script \texttt{train\_model\_v2.py} performs an 80/20 stratified hold-out split with \texttt{random\_state=42}. I compared candidate Decision Tree and Random Forest classifiers using five-fold stratified cross-validation on the training partition, with macro F1 as the selection criterion. Once the candidate with the higher mean cross-validation Macro-F1 was chosen, I measured its behavior on the held-out test portion and then trained a fresh model with the same configuration on the full dataset before saving it as \texttt{exploit\_model.pkl}. This procedure serves three purposes: cross-validation selects the candidate model, the hold-out portion gives an independent check, and the final full-data model is the one actually deployed. I picked tree-based classifiers because the feature space is small, mixed, and non-linear — a tree model can capture threshold effects and interactions among the runtime features (CVSS score, encoded exploit type, and port number) without needing feature scaling. I selected the final classifier empirically using the predefined cross-validation criterion: both candidate models went through the same cross-validation procedure, and the one with the higher mean Macro-F1 score was chosen for deployment. Because several records can correspond to the same CVE identifier, I also ran an additional CVE-grouped cross-validation evaluation, keeping records tied to the same CVE within the same fold so that CVE-level information could not leak between training and validation. I interpret the predictive performance of the exploit-prioritization model in light of the class distribution in the training data. Since the dataset is imbalanced, I based model selection mainly on macro-averaged F1 rather than accuracy alone, since Macro-F1 weighs each priority class equally and is more informative when class frequencies differ this much. This mattered in particular because the Low-priority class is substantially under-represented relative to Medium and High, so overall accuracy alone could easily hide poor performance on that minority class. I also examined class-specific precision, recall, and F1-score during evaluation. I read strong aggregate performance as performance on the evaluated dataset, not as evidence of general predictive reliability across all vulnerability populations. \paragraph{Exploitation Outcome Semantics} The exploitation stage distinguishes between several outcome states so that vulnerability validation is never automatically read as successful exploitation. \texttt{VALIDATED} means supporting evidence was confirmed by a validation mechanism, such as a web-security scanner, without establishing active exploitation. \texttt{EXPLOITED} means an active exploitation method produced a confirmed security outcome, such as validated credentials or a confirmed injectable parameter. \texttt{SESSION\_OBTAINED} is the strongest outcome, where the assessment obtained an interactive Metasploit session that can support later post-exploitation processing. A finding can also be reported as \texttt{CONFIRMED} when its own evidence-producing checker validates the condition without needing a separate exploitation technique. By contrast, \texttt{NOT\_EXPLOITABLE} does not mean the underlying finding is false — it means the current framework simply has no applicable active exploitation method for that finding type. \texttt{FAILED} and \texttt{TIMEOUT} mean an applicable active method was tried but did not produce a confirmed exploitation outcome. This distinction keeps finding validation separate from active exploitation, and it is preserved throughout the exploitation records and the final reporting. \paragraph{Ablation Evaluation of the ML Prioritization Signal} To check how much the machine-learning component actually contributes to exploit prioritization, I ran an ablation experiment against the same target environment under two configurations. In the first, the trained machine-learning model was enabled and its predicted priority probability fed into the exploit-selection score. In the second, I disabled the predictive ML signal and replaced it with a constant neutral value of $P_{\mathrm{ML}}=0.50$ for every candidate. The disabled configuration therefore kept the same ranking formula and the same deterministic evidence while removing the learned model's ability to distinguish between candidates. I compared the two configurations on candidate ordering, selection scores, exploitation outcomes, pipeline completion, ATT\&CK outputs, and total execution time, to see whether the ML component adds measurable prioritization information beyond the deterministic evidence already present in the framework. \subsection{Hybrid MITRE ATT\&CK Classification Method} The MITRE ATT\&CK stage turns vulnerability, exploitation, and post-exploitation evidence into structured ATT\&CK techniques and tactics. The final implementation uses four evidence layers: CVE/CWE evidence enrichment, deterministic rule-based mapping, semantic STIX matching, and TF-IDF-plus-machine-learning classification. A purely rules-based approach would be very precise for known exploitation paths but would cover new or differently described evidence poorly. A purely machine-learning solution could generalize beyond fixed rules, but risks producing inconsistent mappings where an exploit path or CWE already gives stronger technical evidence. The hybrid method I built instead assigns explicit confidence values and favors deterministic evidence whenever sources disagree, as shown in Figure~\ref{fig:mitre-fusion-flow}. % ============================================================ % FIGURE 4 — Hybrid MITRE ATT&CK evidence-validation and classification flow % ============================================================ \begin{figure}[H] \centering \begin{tikzpicture}[node distance=10mm and 8mm] \node[input] (cve) {CVE/CWE\\Evidence\\Enrichment}; \node[input, right=of cve] (rule) {Deterministic\\Rule-Based\\Resolver}; \node[input, right=of rule] (stix) {STIX\\Semantic\\Resolver}; \node[input, right=of stix] (ml) {Machine-\\Learning\\Classifier}; \node[proc, below=16mm of rule, xshift=8mm] (fusion) {Confidence Fusion\\$\text{Score}(T)=\sum_i w_i c_i$}; \node[proc, below=of fusion] (argmax) {$T^{*}=\arg\max_T \text{Score}(T)$}; \node[stage, below=of argmax] (out) {Best Technique +\\Supporting Layers}; \draw[arr] (cve) -- (fusion); \draw[arr] (rule) -- (fusion); \draw[arr] (stix) -- (fusion); \draw[arr] (ml) -- (fusion); \draw[arr] (fusion) -- (argmax); \draw[arr] (argmax) -- (out); \end{tikzpicture} \caption{Hybrid MITRE ATT\&CK evidence-validation and classification flow, combining four evidence layers through weighted confidence fusion.} \label{fig:mitre-fusion-flow} \end{figure} \subsubsection{CVE-to-CWE Evidence Enrichment} \texttt{CVEEnricher} checks the local cache first whenever a valid CVE is attached to an event. If the CVE is not cached, it calls the NVD API to retrieve the associated CWE identifiers and writes the result to \texttt{data/cve\_cache.json}. A local CWE-to-ATT\&CK mapping table then translates the supported weakness types into ATT\&CK techniques with explicit confidence values. When NVD is unavailable, the pipeline keeps going on the local cache if one exists, and this layer simply returns no result for an uncached CVE rather than stopping the assessment. \subsubsection{Deterministic Rule Resolver} The rule resolver holds mappings for CVE prefixes, service names, post-exploitation commands, and exact exploitation modules. I gave the highest deterministic confidence to exact exploit-path evidence, since the executed module itself describes the exploit behavior directly. Other post-exploitation commands — \texttt{hashdump}, \texttt{sysinfo}, \texttt{getuid}, \texttt{getsystem}, \texttt{arp}, and \texttt{ps} — are also mapped directly to ATT\&CK techniques. \subsubsection{STIX Semantic Resolver} The STIX resolver loads the ATT\&CK Enterprise STIX dataset from \texttt{data/en-\newline terprise-attack.json}, downloading it from the MITRE CTI repository if it is missing. At startup it builds an inverted keyword index over the non-revoked, non-deprecated ATT\&CK attack-pattern objects. The vulnerability context it works from includes the exploit path, service, CVE, ExploitDB title, product, and version. \begin{equation} \text{confidence} = \min\big(0.75,\ 0.60 + 0.02 \times \text{raw\_score}\big) \label{eq:stix-confidence} \end{equation} When strong deterministic evidence already exists, I only keep the STIX result if its tactic or technique agrees with that stronger evidence — otherwise the semantic alternative is dropped. If there is no deterministic result at all, a sufficiently confident STIX candidate can proceed to the fusion stage on its own. \subsubsection{Machine-Learning Resolver} The final layer uses TF-IDF text features together with a Random Forest classifier. The classifier predicts an ATT\&CK tactic rather than inventing a specific technique identifier, and the runtime context is normalized the same way as in the training script. The current training procedure relies mainly on ATT\&CK STIX technique descriptions, supplemented with a controlled number of procedure examples and hand-written security examples to strengthen the weaker tactic classes. TF-IDF uses unigrams and bigrams with a bounded vocabulary, and the model itself uses 300 trees, balanced class weights, and a minimum leaf size of two. I chose a Random Forest for this text-classification role because a single decision tree is far too sensitive to individual sparse terms, while the ensemble averages decisions across many trees. Even so, I keep this model below deterministic evidence in the decision hierarchy, since its training text is descriptive ATT\&CK material rather than direct exploitation evidence. If the trained model is unavailable, \texttt{MLClassifier} falls back to a bounded keyword-based approximation, which is marked with a separate source name and given a lower fusion weight. So the machine-learning component acts as a supporting classification layer within ATT\&CK mapping — its output is combined with the other evidence sources and is not used as an independent predictor of real-world adversary behavior. \subsubsection{Evidence Validation and Confidence Fusion} I did not treat all sources as equally authoritative. Deterministic CVE and rule evidence is evaluated for strength first, and STIX and ML evidence are only accepted as supporting evidence when they meet confidence requirements and do not contradict a stronger deterministic tactic. Formally, for a candidate technique $T$, every classification layer $i$ that voted for $T$ contributes its confidence $c_i$ scaled by a fixed source weight $w_i$. The fused score of $T$ is therefore \begin{equation} \text{Score}(T) = \sum_i w_i\, c_i , \qquad T^{*} = \operatorname*{arg\,max}_{T} \text{Score}(T) \label{eq:confidence-fusion} \end{equation} where $T^{*}$ is the technique carried forward as the fused verdict for the finding. Table~\ref{tab:fusion_weights} lists the source weights $w_i$ used by the framework. removes repeated techniques while keeping the strongest confidence and the associated hosts. \texttt{TacticStatistics} counts mapped events per tactic and works out the average confidence, and \texttt{TechniqueStatistics} does the equivalent aggregation per technique, recording the contributing sources along the way. \texttt{CoverageAnalyzer} calculates the tactics reached by the assessment and the number of distinct techniques involved. \texttt{ChainBuilder} groups successful exploitation and post-exploitation evidence according to the ordered Enterprise ATT\&CK phases, and excludes failed exploitation attempts from the achieved attack-chain phases. \texttt{HeatmapGenerator} produces a valid ATT\&CK Navigator layer in JSON. Each technique can carry a score, source, host, and confidence comment, so the assessment result can be opened directly in ATT\&CK Navigator. A detection-engineering bridge is provided by \texttt{SigmaMapper}. This component does not synthesize free-form Sigma YAML rules from natural language — instead, it maps supported ATT\&CK technique identifiers to predefined or locally supplied Sigma detection metadata, including a rule identifier, title, and expected log source. Custom mappings can be loaded from \texttt{data/sigma\_rules}. \subsection{Artificial-Intelligence Methodology} I use artificial intelligence as an assisting layer, not as the authority over the penetration-testing process. AI-assisted functionality in the framework splits into predictive, analytical, and generative roles. Classical machine-learning components support selected ranking and classification tasks — mainly exploit prioritization and MITRE ATT\&CK classification. Other components in the analytical enrichment layer rely on deterministic scoring, similarity, or recommendation logic and are not presented as trained machine-learning models. The local LLM is a separate generative component, restricted to grounded natural-language reporting built from security evidence the earlier pipeline stages have already established. \begin{itemize} \item \textbf{MITRE Predictor:} provides an auxiliary estimate of a likely tactic from the classified context without replacing the primary hybrid ATT\&CK mapping process. \item \textbf{Recommendation Engine:} maps observed tactics and findings to defensive actions. \item \textbf{Explainable AI:} records why a result was produced, including the rule, semantic evidence, or model source that contributed to the decision. \item \textbf{Composite Risk Scorer:} computes a secondary heuristic risk score during the AI-assisted enrichment stage using CVSS, EPSS, KEV status, and exploitation-channel type: \begin{equation} R_{\text{composite}} = \min\big( 100,\, 4\cdot\text{CVSS} + 25\cdot\text{EPSS} + \text{KEV}_{\text{bonus}} + \text{Type}_{\text{bonus}} \big) \end{equation} where $\text{KEV}_{\text{bonus}}$ adds 20 points when the finding is present in the CISA KEV catalog, while $\text{Type}_{\text{bonus}}$ adds 20 for Metasploit, 15 for Hydra, 8 for a web finding, and 3 for a manual finding. This score is an auxiliary analytical value rather than a trained machine-learning prediction. It is calculated in Phase~9 after the primary risk-filtering decision and does not replace or override the Phase~5 Risk Engine. \item \textbf{Adversary Similarity:} compares the set of observed ATT\&CK techniques $A$ with the stored technique set of a known adversary profile $B$ (e.g.\ APT28, APT29, Lazarus, FIN7, Volt Typhoon) using Jaccard similarity: \begin{equation} J(A,B) = \frac{|A \cap B|}{|A \cup B|} \label{eq:jaccard-similarity} \end{equation} The adversary profiles are then ranked by $J(A,B)$, and the highest-scoring profile is reported as the closest behavioural match to the observed technique set. \item \textbf{LLM Report Writer:} converts already-decided security results into natural-language report sections using Qwen2.5 through a local Ollama service. \end{itemize} The recommendation component maps defensive actions to the observed tactic. Table~\ref{tab:recommendations} shows a couple of example entries. \begin{table}[htbp] \centering \caption{Example recommendation-table entries} \label{tab:recommendations} \begin{tabularx}{\textwidth}{l X} \hline \textbf{Tactic} & \textbf{Recommendation} \\ \hline Initial Access & Patch public-facing services; enable WAF and input validation \\ Credential Access & Enable MFA; enforce strong password policy \\ \hline \end{tabularx} \end{table} So classical ML supports ranking and classification here, while the LLM handles grounded natural-language reporting and never acts as a security-decision authority. \subsection{LLM-Based Report Writing} I deliberately placed the local LLM after risk calculation and ATT\&CK classification, with the boundary enforced in \texttt{summary\_builder.py}. This module reduces the raw pipeline output down to a small set of already-decided fields — the highest-priority findings, mapped ATT\&CK techniques, the risk summary, and the attack-chain summary — and it does not make any new severity, CVSS, risk, KEV, or ATT\&CK decisions of its own. These structures are then passed to \texttt{report\_writer.py}, which uses separate prompt templates for the executive summary, the technical ATT\&CK analysis, and the remediation recommendations. The current local provider is Qwen2.5 accessed through Ollama. I chose this design specifically to avoid handing security-critical decisions to a generative model. The reporting layer also fails gracefully: if Ollama cannot be reached, the structured findings, risk values, ATT\&CK mappings, and other deterministic outputs all remain valid — only the natural-language narrative becomes unavailable. \subsection{Experimental Post-Exploitation ML Component} I also developed a separate post-exploitation next-action model as an experimental machine-learning component. It is trained on post-exploitation state information and is meant to predict the next suitable action class from features describing the compromised system and prior observations. The training script compares several classifiers — Random Forest, Extra Trees, and Gradient Boosting, plus optional XGBoost and LightGBM candidates when those libraries happen to be installed. The data is split using a stratified hold-out partition, model comparison uses stratified cross-validation and macro F1, and the number of folds is reduced automatically when the smallest class cannot support the requested fold count. I am treating this model as a developed experimental component rather than as a mandatory decision-maker in the current twelve-stage runtime. The production post-exploitation phase continues to run on its implemented module logic and ATT\&CK post-exploitation mapping. \subsection{Supporting Machine-Learning Validation} Even though detailed machine-learning performance is not used as a primary framework-level metric, I still developed the internal models using standard classification measures during training. For a classification model, accuracy is calculated as: \begin{equation} Accuracy = \frac{TP + TN} {TP + TN + FP + FN} \end{equation} Precision is calculated as: \begin{equation} Precision = \frac{TP} {TP + FP} \end{equation} Recall is calculated as: \begin{equation} Recall = \frac{TP} {TP + FN} \end{equation} The F1-score is calculated as: \begin{equation} F1 = 2 \times \frac{Precision \times Recall} {Precision + Recall} \end{equation} I used these measures internally while training and comparing classifiers; they are not the principal end-to-end performance criteria for the complete framework. \section{Project Design} \label{sec:project-design} This section translates the methodology into the actual software architecture. The project is a modular Python framework controlled by \texttt{engine/main.py}. The same execution engine is also reachable through a FastAPI backend and can be deployed through Docker Compose. \subsection{System Configuration Parameters} Runtime parameters are centralized in \texttt{engine/config/settings.py}. I centralized the settings this way specifically to avoid scattering experiment-specific values across the modules, which makes an assessment much easier to reproduce. \begin{table}[htbp] \centering \caption{Principal system configuration parameters} \label{tab:configuration_parameters} \small \begin{tabularx}{\textwidth}{l X X} \hline \textbf{Group} & \textbf{Parameter} & \textbf{Value} \\ \hline Reconnaissance & Host-discovery args & \texttt{-sn} \\ Reconnaissance & Recon timeout & 30 s \\ Reconnaissance & Maximum hosts & 256 \\ Scanning & Scan args & \texttt{-sV -sC -O --open -T4} \\ Scanning & Scanned ports & Top 1000 \\ Scanning & Scan timeout & 120 s \\ Risk & Risk threshold & 30 \\ Risk & CVSS bands & C9, H7, M4 \\ Risk & Risk bands & C80, H60, M40 \\ Exploitation & Default LHOST / LPORT & \texttt{127.0.0.1 / 4444} \\ Exploitation & Exploit timeout & 60 s \\ MITRE / ML & ML confidence threshold & 0.55 \\ Persistence & Default database & SQLite \\ Attack Graph & \texttt{NEO4J\_ENABLED} & false by default \\ Database & \texttt{DATABASE\_URL} & SQLite URL by default \\ Server & API host / port & \texttt{0.0.0.0:8000} \\ \hline \end{tabularx} \end{table} The host-discovery argument \texttt{-sn} drives Nmap ping-sweep host discovery. The Hybrid MITRE Evidence-Fusion Algorithm evaluates the strongest available evidence alongside the supporting classification layers. The overall decision can be written as: \begin{equation} E^* = \operatorname*{arg\,max}_{E_i} \left( Confidence(E_i) \right) \end{equation} where $E_i$ is an available classification evidence source and $E^*$ is the evidence selected after validation and fusion. The Multi-Factor Risk Algorithm calculates the composite risk for each finding and then sorts the findings by that risk score: \begin{equation} F_{\mathrm{sorted}} = \operatorname{sort} \left( F,\, RiskScore(F) \right) \end{equation} in descending order of risk score. Similarly, the Exploit Prioritization Algorithm calculates a selection score for the technically feasible exploitation candidates and sorts them in descending order: \begin{equation} E_{\mathrm{sorted}} = \operatorname{sort} \left( E,\, SelectionScore(E) \right) \end{equation} \subsection{Software Component Design} The system uses a modular software architecture in which each major security function is its own independent component. A central controller in \texttt{engine/main.py} instantiates the components it needs and passes structured findings from one stage to the next. This modular layout separates reconnaissance, scanning, vulnerability analysis, exploitation, post-exploitation, MITRE ATT\&CK classification, artificial-intelligence processing, graph analysis, social-engineering simulation, and reporting into distinct pieces. I added this API layer specifically to keep the user-facing interface separate from the security engine itself, so the same assessment pipeline can be started without putting any control logic inside the HTTP layer. On start-up, the main application enables CORS middleware and initializes the database once, then forwards every scan request to a dedicated service layer instead of running the pipeline directly inside the endpoint handler. As a result, each request follows a clear, one-directional flow: \begin{equation} \begin{aligned} \text{HTTP Request} \rightarrow \texttt{start\_scan()} \rightarrow \texttt{run\_pipeline()} \\ \rightarrow\ \text{Session Storage} \rightarrow \text{API Response} \end{aligned} \end{equation} The backend is organized into topic-specific routers, each exposing one category of results: vulnerabilities, MITRE ATT\&CK findings, the reconstructed attack chain, analytics, the attack graph, threat-intelligence data, generated reports, live activity updates, dashboard information, and the scan-control operations themselves. Since these routes are declared with typed schemas, FastAPI generates interactive OpenAPI documentation automatically, giving both Swagger UI and ReDoc without any extra effort on my part. Each completed assessment is bound to a unique session identifier. The \texttt{/scan} endpoint starts a run, and session-scoped endpoints return the corresponding results or the generated report on demand. The same identifier carries through into the persistent database records and into the report file paths, so the API response, the stored data, and the generated artefacts all stay linked to a single engagement. \subsection{Database Design} \label{sec:db} Persistence runs through SQLAlchemy ORM models together with a repository-oriented access layer, which keeps each module's business logic separate from the details of data storage. The assessment session sits at the center of the schema: every other record carries the identifier of the session it belongs to, so the full output of a single run can be reconstructed as one coherent, time-ordered account. The one-to-many relationship between a session and its findings mirrors the structure of the assessment itself: a single engagement produces many vulnerabilities, and each of those can in turn lead to exploitation results and classified techniques. \subsection{Attack Graph Design} \label{sec:graph} The attack-graph stage turns the exploitation results and the reconstructed attack-chain evidence into a set of graph nodes and relationships that show how the observed compromise unfolded. By default this graph is analyzed entirely in memory, which is enough for the scale of a controlled laboratory assessment and keeps the stage free of external dependencies. Neo4j support is available as an optional backend and only activates when \texttt{NEO4J\_ENABLED} is set to \texttt{true}, in which case the connection details are read from \texttt{NEO4J\_URI}, \texttt{NEO4J\_USER}, and \texttt{NEO4J\_PASSWORD}. When Neo4j is disabled, the stage simply continues with its in-memory representation rather than failing, so graph analysis stays available whether or not the optional database is present. \subsection{Deployment Architecture} \label{sec:deploy} The project ships with a Docker Compose deployment that separates the interactive scanner from the web API and keeps optional infrastructure outside the default runtime. This lets a user run either the service-oriented API or the interactive scanner without spinning up components a given experiment does not need. The deployment consists of the following services: \begin{itemize} \item \textbf{API Service:} exposes FastAPI on port~8000 and mounts persistent directories for reports, logs, database files, models, and project data. \item \textbf{CLI Scanner Service:} runs \texttt{python -m engine.main} with host networking and interactive terminal support for direct, hands-on assessments. \item \textbf{Neo4j Service:} an optional graph database, enabled through the \texttt{with-graph} Compose profile. \item \textbf{PostgreSQL Service:} an optional relational database, enabled through the \texttt{with-db} profile. \end{itemize} The API container starts from a conservative default configuration in which the optional graph database is disabled and SQLite is used for persistence: \begin{verbatim} NEO4J_ENABLED=false DATABASE_URL=sqlite:///database/redteam.db \end{verbatim} Persistent volumes make sure reports, logs, model files, and database contents are not tied to the lifetime of a single container, so results survive container restarts and rebuilds. \subsection{Reporting Design} \label{sec:reporting} The final reporting stage brings machine-readable and human-readable outputs together. On the structured side, the framework emits a JSON assessment report, a PDF assessment report, an ATT\&CK Navigator layer in JSON, an ordered ATT\&CK attack-chain description, the persisted vulnerability, exploitation, and MITRE records, and the coverage and risk summaries. These are deterministic products of the pipeline and can be consumed directly by other tools. The human-readable path relies on the bounded LLM workflow introduced earlier in this chapter. The generated narrative includes an executive summary, a technical ATT\&CK analysis, and a set of recommendations. Each section is produced strictly from the structured pipeline result, and none of it feeds back into any earlier security decision. This ordering guarantees the narrative can explain and present the findings without ever changing the severity, risk, or ATT\&CK values the analytical stages already established. \subsection{End-to-End Workflow Description} \label{sec:workflow} At run time, the controller entry point \texttt{run\_pipeline(target, lhost)} resets the progress state, creates a unique session identifier, and records a new scan activity. Execution then proceeds through the twelve stages in strict order, with each stage consuming the structured output of the one before it. Because \texttt{run\_pipeline()} is a single, deterministic entry point, the wall-clock time of a complete run can be measured by timing this call from the caller — for example, from the CLI driver or the FastAPI service layer. The current implementation does not itself instrument or persist a per-run duration internally, so this timing has to be applied externally around the call rather than emitted as an output field of the pipeline. In Phase~1, reconnaissance discovers the live hosts within the target scope. In Phase~2, network scanning and the OWASP web-security analysis run together: the web scan registers its seven specialized checkers and invokes \texttt{TechnologyDetector}. Phase~3 maps the discovered services to candidate findings and merges the OWASP findings into a single, common finding list. Phase~4 enriches every finding with CVSS, EPSS, KEV, and the project threat score, and Phase~5 applies the Risk Engine, keeping only the findings that clear the configured threshold. Phase~6 ranks and executes the exploitation candidates using a selection score that combines CVE match confidence, EPSS, normalized CVSS, exploitation reliability, KEV status, and the machine-learning priority probability. Phase~7 performs post-exploitation whenever a usable session is obtained, keeping the executed post-exploitation commands as ATT\&CK evidence. Phase~8 initializes the hybrid MITRE ATT\&CK engine, where the CVE/CWE evidence, the deterministic rules, the STIX semantic matching, and the machine-learning classification are all evaluated under the evidence-validation policy. The resulting techniques are merged, the attack chain is reconstructed, the Navigator heatmap and attack-chain JSON files are saved, coverage is computed, and the confirmed techniques are forwarded to \texttt{SigmaMapper}. Phase~9 runs the AI-assisted enrichment pipeline; Phase~10 builds and analyzes the attack graph, using Neo4j only when it is enabled; and Phase~11 runs the social-engineering simulation module. Finally, Phase~12 assembles the risk summary, generates the JSON and PDF reports, and stores the assessment records in the database. Throughout the run, every stage's output accumulates in a shared session context, so each later stage works with the complete findings of all the earlier ones. The pipeline is also guarded by explicit halt conditions at each critical point: whenever a stage produces no usable result, the run stops gracefully instead of pressing on with empty data. This discipline keeps every assessment bounded, predictable, and reproducible — which is itself a precondition for the controlled evaluation reported in Chapter~4. \subsection{Implementation Reliability Check} \label{sec:reliability} The methodology also defines an automated test pass rate as an indicator of software correctness: \begin{equation} \text{Test Pass Rate} = \frac{\text{Tests Passed}}{\text{Total Tests Executed}} \times 100\% \end{equation} I keep this measure as an indicator of implementation quality that reflects the correctness of the framework as a piece of software. I deliberately separate it from the principal end-to-end performance measures defined in Section~\ref{sec:metrics}, because it reports on the health of the code rather than on the operational behavior of the assessment pipeline as a whole. \section{Performance Metrics} \label{sec:metrics} I organized the experimental validation at two levels. First, I ran repeated complete runs against the primary laboratory target under the same configuration to examine execution-time repeatability and the consistency of the main framework outputs. I summarized these repeated runs using basic descriptive statistics — mean, standard deviation, minimum, and maximum execution time. Second, I evaluated the framework across more than one deliberately vulnerable target environment to see whether the same orchestration workflow could operate across different network- and web-oriented attack surfaces. The cross-target comparison focuses on observable framework outputs — findings, ATT\&CK coverage, pipeline completion, execution time — rather than on any statistical generalization between target classes. I deliberately limited the evaluation in Chapter~4 to a small set of measurements that can be observed directly from the implemented framework. Keeping the evaluation this narrow means every reported figure stays traceable to a concrete runtime value or capability, rather than to an idealized description of the system. I use five evaluation dimensions, matching the Sub-Objectives from Chapter~1: execution time, exploitation success rate, MITRE ATT\&CK coverage, automation and pipeline completion, and a functional comparative analysis. Each is described in turn below. \subsection{Execution Time} Execution time is the wall-clock duration of a complete pipeline run, from the invocation of \texttt{run\_pipeline(target, lhost)} to the completion of Phase~12 (or to an earlier explicit halt condition): \begin{equation} T_{\text{total}} = t_{\text{end}} - t_{\text{start}} \end{equation} When repeated runs are available under the same configuration, I summarize execution time using the mean, standard deviation, minimum, and maximum values to describe the variation observed between runs. Since the pipeline is not internally instrumented with a persisted timer, $t_{\text{start}}$ and $t_{\text{end}}$ are recorded externally by the caller around the single \texttt{run\_pipeline()} entry point — which is sufficient, since the twelve phases execute sequentially within that one call. Where a finer analysis is needed, the duration of each individual stage can be measured the same way, by timing the corresponding phase boundaries in the controller. \subsection{Active Exploitation Success Rate} Because the framework distinguishes active exploitation from finding validation, this metric only includes findings for which an active exploitation method was actually attempted. Scanner validation and findings confirmed independently by OWASP-oriented checkers are not counted as successful exploits. I define the Active Exploitation Success Rate (AESR) as: \begin{equation} \text{AESR} = \frac{N_{\text{successful active exploitation attempts}}} {N_{\text{active exploitation attempts}}} \times 100\% \end{equation} Successful active outcomes include \texttt{EXPLOITED} and \texttt{SESSION\_OBTAINED}. A \texttt{VALIDATED} result does not count as successful exploitation, since it only confirms supporting security evidence without establishing an exploitation outcome. Similarly, a finding confirmed directly by an OWASP checker without a separate exploitation attempt is excluded from both the AESR numerator and denominator. \texttt{FAILED} and \texttt{TIMEOUT} outcomes are included in the denominator whenever an active exploitation method was attempted. \texttt{NOT\_EXPLOITABLE} findings are excluded, since no applicable exploitation method was ever executed against them. To describe the broader evidence-confirmation behavior separately, the framework can also report a Finding Confirmation Rate: \begin{equation} \text{Finding Confirmation Rate} = \frac{N_{\text{findings confirmed by active exploitation or validation evidence}}} {N_{\text{findings for which confirmation was evaluated}}} \times 100\%. \end{equation} These two measures answer different questions: AESR evaluates how successful the active exploitation attempts were, while the Finding Confirmation Rate describes how many evaluated findings received supporting confirmation evidence of any kind. \subsection{Automation Level and Pipeline Completion Rate} The pipeline consists of twelve defined phases, executed in strict sequence by the central controller. Pipeline completion for a given run is determined by how far execution proceeded before either reaching Phase~12 (Reporting) or being stopped by one of the explicit halt conditions described in Section~\ref{sec:overall-methodology} (no live host, no usable scan/web results, or no findings above the risk threshold): \begin{equation} \text{Pipeline Completion Rate} = \frac{\text{Highest Phase Reached}}{\text{Total Pipeline Phases (12)}} \times 100\% \end{equation} A completion rate of 100\% therefore corresponds to a run that reached Phase~12 and produced a final report, while a lower value corresponds to a run that was halted earlier by one of the explicit stop conditions. I assess automation qualitatively alongside the completion rate. Once an assessment run has been initiated, the implemented transitions between pipeline stages proceed automatically, without requiring the analyst to manually transfer outputs from one stage to the next. So the framework demonstrates automated stage-to-stage orchestration for the selected complete runs. This statement is about pipeline coordination and should not be read as a universal 100\% automation rate across all underlying tools, infrastructure dependencies, external data sources, or target conditions. The current implementation reports this outcome through its console and log output rather than through a dedicated numerical counter; any future version of the framework that needs per-phase telemetry across many runs would have to add such a counter explicitly. For the selected complete assessment run, all twelve defined pipeline phases were reached: \[ \text{Pipeline Completion} = \frac{12}{12}\times 100 = 100\%. \] This value refers to the selected complete run and should not be read as a universal completion rate across all possible targets, since the framework contains explicit halt conditions whenever no usable evidence is available. \subsection{Observed ATT\&CK Tactic Coverage} As defined earlier in this chapter, the coverage reported in this study is the observed ATT\&CK tactic coverage within the tested assessment evidence: the proportion of the ATT\&CK tactics modeled by the framework that were represented by mapped evidence during a particular assessment: \begin{equation} \text{Observed ATT\&CK Tactic Coverage} = \frac{N_{\text{observed tactics}}} {N_{\text{modeled tactics}}} \times 100\%. \end{equation} Only tactics tied to valid MITRE ATT\&CK technique identifiers are included in this metric. Auxiliary classifier labels or fallback identifiers that do not correspond to official ATT\&CK technique IDs are excluded from both the technique count and the observed tactic coverage. I interpret coverage as a descriptive measure of the behavioral breadth captured by valid ATT\&CK mappings in a given assessment, not as classification accuracy, and not as a measure where a higher percentage automatically means better framework performance. \subsection{Functional Comparative Analysis} The final evaluation dimension is qualitative rather than statistical. Here I compare the framework with widely used security platforms such as Metasploit, OpenVAS, and MITRE Caldera in terms of functional scope, looking at whether each one provides capabilities such as network reconnaissance, vulnerability discovery, exploitation, threat-intelligence enrichment, ATT\&CK mapping, risk-based prioritization, attack-chain construction, AI-assisted reporting, and integrated result persistence. The point of this comparison is not to argue that this academic framework replaces mature, production-grade platforms. It is meant to position the contribution of this work by showing which functions have been brought together into one coherent workflow, as opposed to functions that are normally handled by separate, specialized tools. \section{Summary} \label{sec:summary} This chapter has set out the methodology and design behind the proposed \textbf{Hybrid Rule-Based and AI-Assisted Penetration Testing Orchestration Framework}. The work follows a combined developmental and experimental approach: I first built a working security framework, then evaluated it inside an isolated laboratory environment. At the center of the methodology is a twelve-stage automated pipeline. Reconnaissance and network scanning establish the target context, while an integrated OWASP engine adds seven specialized web-security checks together with technology fingerprinting. The network and web findings are merged before threat-intelligence enrichment and multi-factor risk assessment, after which a separate exploit-prioritization mechanism orders the high-risk findings by combining evidence-based factors with a bounded machine-learning probability. I advanced the MITRE ATT\&CK methodology from a simple lookup process into a four-layer hybrid design. CVE/CWE evidence and deterministic rules supply the strongest mappings, STIX provides semantic evidence, and a TF-IDF Random Forest model contributes a weaker classification signal. Semantic and machine-learning evidence is validated against the stronger deterministic mappings before being combined through weighted confidence fusion. The resulting ATT\&CK data then feeds into technique and tactic statistics, an attack chain, an ATT\&CK Navigator heatmap, coverage information, and Sigma-based detection mappings. I intentionally split artificial intelligence into supporting analytical and generative roles. The AI-assisted enrichment components support prediction, explanation, recommendation, and adversary similarity, while the Qwen2.5 model served through Ollama is restricted to report writing — it receives condensed, previously calculated findings through the summary-building layer and produces executive, technical, and recommendation text without altering any severity, risk, or ATT\&CK decision. At the design level, the same core engine is exposed through both a command-line execution path and a FastAPI REST architecture. Assessments are session-based, stored through SQLAlchemy models, and reported in JSON and PDF formats, with Docker Compose providing separate API and CLI scanner services alongside optional Neo4j and PostgreSQL profiles. Finally, I kept the experimental evaluation deliberately focused. Chapter~4 uses total execution time, active exploitation success rate, observed MITRE ATT\&CK tactic coverage, automation and pipeline completion, and a functional comparative analysis. Each of these measurements maps directly onto a value or capability the framework actually implements, which keeps the final evaluation reproducible without introducing metrics disconnected from the system's real runtime behavior.
